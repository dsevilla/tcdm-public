Sesión 3 — Un data lake sobre almacenamiento S3-compatible

En la sesión anterior trabajamos con ficheros Parquet almacenados en HDFS. Ahora conservaremos el mismo formato y el mismo conjunto de datos, pero cambiaremos el sistema de almacenamiento: los objetos se guardarán en un servicio compatible con la API de Amazon S3.

El objetivo es aprender qué cambia al pasar de un sistema de ficheros distribuido a un almacenamiento de objetos y qué partes del código pueden mantenerse al migrar posteriormente a Amazon S3. Esta sesión construye un data lake sobre S3: conserva los Parquet como objetos bajo prefijos. Las sesiones 6 y 7 añadirán la gestión de tablas, esquemas y snapshots para construir un lakehouse.

Objetivos

Al terminar la sesión deberías poder:

  • explicar la diferencia entre un bloque HDFS y un objeto S3;
  • distinguir un bucket, una clave de objeto y un prefijo;
  • arrancar y detener un almacenamiento S3 local sin modificar el clúster Hadoop;
  • utilizar la API estándar de AWS para listar buckets, consultar objetos y leer una parte de un objeto;
  • copiar los Parquet deterministas de TPC-DS SF1 desde HDFS hasta S3;
  • leer los mismos Parquet desde S3 con PyArrow, Polars y DuckDB;
  • parametrizar un programa para usar RustFS local o Amazon S3 real;
  • borrar y regenerar el data lake sin confundir sus datos con los del warehouse HDFS.

Del data lake HDFS al data lake S3

En S2 los datos se encontraban en una ruta del espacio de nombres HDFS:

hdfs:///datalake/raw/tpcds/date_dim/part-...

En S3 se guardarán en un bucket y una clave de objeto:

s3://tcdm-datalake/raw/tpcds/date_dim/part-...

Se conserva así la misma arquitectura medallion: raw identifica la capa, tpcds la fuente y date_dim la tabla. Los prefijos silver/ y gold/ aparecerán cuando se escriban objetos en esas capas; no hace falta crear directorios vacíos ni objetos marcadores.

La apariencia de directorios es una convención. S3 no necesita crear un directorio date_dim: el texto separado por / forma parte de la clave del objeto. Esto tiene consecuencias prácticas:

  • HDFS ofrece operaciones de sistema de ficheros, permisos y bloques replicados entre DataNodes.
  • S3 ofrece objetos identificados por claves dentro de buckets y operaciones HTTP, como GET, PUT, HEAD y listados por prefijo.
  • una herramienta puede mostrar una jerarquía de carpetas aunque el servicio solo esté almacenando nombres de objetos;
  • la consistencia, las operaciones de renombrado y la gestión de permisos no deben suponerse idénticas a las de HDFS.

Los ficheros Parquet no cambian al copiarlos. Continúan teniendo su esquema, metadatos y firmas PAR1, pero ahora el lector los obtiene mediante la API de objetos. El prefijo agrupa físicamente la colección de objetos Parquet que corresponde a date_dim.

El servicio local RustFS

Usaremos RustFS como almacenamiento S3-compatible local. La elección permite trabajar con clientes estándar de AWS mediante un servicio aislado conectado a la red del laboratorio. El Compose de esta sesión está en entorno/compose-s3.yml y contiene únicamente:

Servicio Función ¿Permanece ejecutándose?
rustfs-s3 API S3 y consola web Sí
bucket-setup-s3 Crea el bucket si todavía no existe No, termina correctamente
s3-client Contenedor con AWS CLI para las órdenes de la sesión Sí

El servicio usa un volumen Docker llamado tcdm-26-27-rustfs-s3-data. Detener los contenedores no borra los objetos. El comando down -v, en cambio, elimina también ese volumen y debe reservarse para regenerar completamente el ejercicio.

Este Compose no necesita montar scripts ni ficheros de configuración del host: los contenedores auxiliares reciben su configuración mediante variables de entorno y los objetos se conservan en un volumen nombrado. Por eso no hay que crear rutas adicionales antes de arrancarlo, tampoco en Docker Desktop para macOS. En el Compose posterior que añade Trino y Polaris se aplica la misma precaución: HDFS y S3 tienen directorios de configuración separados y cada Trino monta un único directorio completo de configuración, cuyo subdirectorio catalog contiene sus catálogos.

La versión se puede cambiar mediante RUSTFS_VERSION en .env. La versión incluida es la seleccionada para el curso. Las credenciales del Compose solo sirven para el laboratorio local.

Arrancar el clúster y S3

S3 reutiliza los Parquet que S2 genera en HDFS. Primero debe estar arrancado el clúster Hadoop y debe existir el dataset de origen que deja el notebook de S2. Desde la raíz de la distribución de sesiones sólo hay que arrancar la infraestructura que no puede iniciar un kernel sin acceso al Docker del host:

make -C entorno warehouse-up   # sólo si Hadoop no sigue activo desde S2
make -C entorno s3-up

La red hadoop-cluster se utiliza para conectar los contenedores, pero RustFS no es un DataNode ni un NodeManager. Es simplemente otro servicio accesible desde los contenedores del laboratorio. Los puertos publicados son:

Servicio Dirección
API S3 http://localhost:9000
Consola RustFS http://localhost:9001

La consola permite inspeccionar visualmente los buckets y objetos. Las órdenes reproducibles deben hacerse con AWS CLI o con un SDK, porque esa es la interfaz que se podrá reutilizar con AWS.

RustFS almacena los objetos Parquet y sus prefijos. La sesión observa esa organización física directamente mediante la consola, AWS CLI y los lectores Python.

Crear el data lake S3 a partir de HDFS

El propio s3.ipynb hace el trabajo de datos: comprueba que S2 dejó las 24 tablas, enumera los ficheros excluyendo _SUCCESS, limpia el prefijo de destino y copia cada Parquet al bucket tcdm-datalake. De este modo el mismo código que ve el alumnado es el que ejecuta CI. El flujo de un fichero es:

hdfs dfs -cat fichero.parquet
        │ flujo binario
        ▼
boto3.upload_fileobj(...) -> s3://tcdm-datalake/raw/tpcds/tabla/fichero

La celda usa una enumeración recursiva:

hdfs dfs -ls -R /datalake/raw/tpcds \\
  | awk '$1 ~ /^-/ && $NF !~ /\\/_SUCCESS$/ { print $NF }'

La salida de hdfs dfs -ls empieza por - para los ficheros y por d para los directorios. El filtro conserva sólo los primeros y excluye _SUCCESS, que es un marcador de la generación y no un fichero Parquet.

Después, para cada ruta, hdfs dfs -cat envía los bytes a boto3.upload_fileobj. El fichero no se copia primero al sistema de ficheros de namenode ni al host. Al terminar, el notebook exige que el número de objetos coincida con el de fragmentos fuente y ejecuta las lecturas con PyArrow, Polars y DuckDB.

Podemos observar los objetos desde el contenedor con AWS CLI:

docker exec tcdm-s3-client aws --endpoint-url http://rustfs:9000 \
  s3api list-objects-v2 \
  --bucket tcdm-datalake \
  --prefix raw/tpcds/date_dim/

También podemos utilizar la misma API desde el equipo anfitrión si tenemos instalado AWS CLI:

AWS_ACCESS_KEY_ID=tcdm_student \
AWS_SECRET_ACCESS_KEY=tcdm_student_secret \
aws --endpoint-url http://localhost:9000 \
  s3api list-buckets

El endpoint es la única parte especial del laboratorio local. El comando usa s3api, no una operación propia de RustFS.

Comprobar la API de AWS con boto3

El programa check_s3_api.py muestra operaciones básicas de un cliente S3. Se ejecuta desde namenode, porque ese contenedor comparte la red Docker con RustFS y será también el lugar desde el que lanzaremos Spark posteriormente.

Creamos un entorno virtual para la sesión y copiamos el programa:

docker exec namenode su - luser -c \
  'python3 -m venv /home/luser/.venv-tcdm-s3'
docker cp s3/requirements.txt \
  namenode:/tmp/tcdm-s3-requirements.txt
docker cp s3/check_s3_api.py \
  namenode:/tmp/check_s3_api.py
docker exec namenode chown luser:hadoop \
  /tmp/tcdm-s3-requirements.txt /tmp/check_s3_api.py
docker exec namenode su - luser -c \
  '/home/luser/.venv-tcdm-s3/bin/python -m pip install \
   -r /tmp/tcdm-s3-requirements.txt'

El fichero requirements.txt fija versiones compatibles de boto3, aiobotocore, fsspec y s3fs para que la instalación sea reproducible.

Dentro de namenode, el nombre DNS es rustfs, no localhost:

docker exec -u luser \
  -e AWS_ENDPOINT_URL=http://rustfs:9000 \
  -e AWS_ACCESS_KEY_ID=tcdm_student \
  -e AWS_SECRET_ACCESS_KEY=tcdm_student_secret \
  namenode /home/luser/.venv-tcdm-s3/bin/python /tmp/check_s3_api.py \
  tcdm-datalake raw/tpcds/date_dim --minimum-objects 1

El programa realiza y muestra list_buckets(), list_objects_v2(), head_object() y get_object(Range="bytes=0-3"). La última respuesta debe ser b'PAR1': confirma que el objeto remoto comienza con la firma de Parquet y que el acceso por rangos funciona.

Lectura con PyArrow

read_s3_pyarrow.py utiliza s3fs, que implementa el acceso S3 mediante el SDK de AWS, y adapta ese filesystem a PyArrow mediante FSSpecHandler:

PyArrow Parquet
      │
      ▼
FSSpecHandler
      │
      ▼
s3fs → botocore → API S3
docker cp s3/read_s3_pyarrow.py namenode:/tmp/read_s3_pyarrow.py
docker exec namenode chown luser:hadoop /tmp/read_s3_pyarrow.py
docker exec -u luser \
  -e AWS_ENDPOINT_URL=http://rustfs:9000 \
  -e AWS_ACCESS_KEY_ID=tcdm_student \
  -e AWS_SECRET_ACCESS_KEY=tcdm_student_secret \
  namenode /home/luser/.venv-tcdm-s3/bin/python /tmp/read_s3_pyarrow.py \
  tcdm-datalake raw/tpcds/date_dim \
  --key-column d_date_sk --expected-rows 73049

El programa lista las claves Parquet, lee todos los fragmentos, imprime el esquema y cinco filas, y calcula filas, claves no nulas, mínimo, máximo y suma de la clave. Esas medidas deben coincidir con las obtenidas en S2.

El patrón de búsqueda termina en /, no en /.parquet. Algunos escritores de Trino generan ficheros Parquet sin esa extensión; en ese caso sigue siendo posible reconocerlos por la firma binaria PAR1. Por eso los lectores enumeran los objetos del prefijo y excluyen explícitamente _SUCCESS, que es un marcador y no contiene datos Parquet.

Lectura con Polars

read_s3_polars.py utiliza el mismo s3fs para localizar los objetos, abre cada fichero como flujo binario y lo entrega a polars.read_parquet(). La operación concatena los fragmentos en un DataFrame:

docker cp s3/read_s3_polars.py namenode:/tmp/read_s3_polars.py
docker exec namenode chown luser:hadoop /tmp/read_s3_polars.py
docker exec -u luser \
  -e AWS_ENDPOINT_URL=http://rustfs:9000 \
  -e AWS_ACCESS_KEY_ID=tcdm_student \
  -e AWS_SECRET_ACCESS_KEY=tcdm_student_secret \
  namenode /home/luser/.venv-tcdm-s3/bin/python /tmp/read_s3_polars.py \
  tcdm-datalake raw/tpcds/date_dim \
  --key-column d_date_sk --expected-rows 73049

La concatenación facilita el primer ejercicio, pero reúne todas las filas en memoria. Más adelante usaremos lecturas lazy y Spark para trabajar con colecciones mayores.

Lectura SQL con DuckDB

DuckDB puede consultar Parquet sin crear una tabla permanente. Su extensión nativa httpfs accede directamente a la API S3. El programa carga la extensión, configura un secreto S3 con el endpoint, las credenciales y el estilo de URL, y después consulta las URLs s3:// directamente. El contenido sigue siendo el mismo Parquet y el endpoint puede ser RustFS local o Amazon S3.

docker cp s3/read_s3_duckdb.py namenode:/tmp/read_s3_duckdb.py
docker exec namenode chown luser:hadoop /tmp/read_s3_duckdb.py
docker exec -u luser \
  -e AWS_ENDPOINT_URL=http://rustfs:9000 \
  -e AWS_ACCESS_KEY_ID=tcdm_student \
  -e AWS_SECRET_ACCESS_KEY=tcdm_student_secret \
  namenode /home/luser/.venv-tcdm-s3/bin/python /tmp/read_s3_duckdb.py \
  tcdm-datalake raw/tpcds/date_dim \
  --key-column d_date_sk --expected-rows 73049

La consulta conceptual es:

DESCRIBE SELECT * FROM read_parquet([...]);
SELECT * FROM read_parquet([...]) LIMIT 5;
SELECT count(*), min(d_date_sk), max(d_date_sk), sum(d_date_sk)
FROM read_parquet([...]);

Aquí el catálogo no sabe nada de date_dim: DuckDB recibe directamente la lista de objetos Parquet. La lista se obtiene mediante list_objects_v2 y la lectura la realiza httpfs, no s3fs.

Comparar los resultados

Las tres herramientas deben producir la misma firma:

(filas, claves_no_nulas, mínimo, máximo, suma)

PyArrow proporciona una representación columnar explícita; Polars construye un DataFrame; DuckDB ejecuta un plan SQL. Las tres terminan leyendo los mismos objetos Parquet y por eso pueden compararse mediante una métrica común.

Conviene hacer también una lectura selectiva:

import polars as pl

with filesystem.open("tcdm-datalake/raw/tpcds/date_dim/part-00000", "rb") as stream:
    sample = pl.read_parquet(stream, columns=["d_date", "d_year"])
print(sample.head())

Leer solo dos columnas reduce los bytes de columnas que deben decodificarse, porque Parquet es columnar. Más adelante combinaremos esta propiedad con filtros y particiones en Spark, Trino e Iceberg.

Configuración local y configuración AWS

Los programas leen la configuración mediante variables estándar del SDK:

Variable RustFS local Amazon S3
AWS_ENDPOINT_URL http://rustfs:9000 dentro de Docker normalmente no se define
AWS_ACCESS_KEY_ID tcdm_student credencial IAM del laboratorio o rol
AWS_SECRET_ACCESS_KEY secreto local del Compose secreto temporal o rol IAM
AWS_SESSION_TOKEN no se define token temporal del laboratorio, si existe
AWS_DEFAULT_REGION us-east-1 región del bucket
AWS_S3_ADDRESSING_STYLE path dentro de Docker preferentemente virtual

El código utiliza las variables estándar del SDK y no invoca APIs propias de RustFS. En Amazon S3 se configura el bucket, la región y las credenciales IAM del laboratorio. RustFS permite comprobar localmente el protocolo y el flujo de datos; la seguridad de una cuenta AWS requiere sus propios servicios y políticas.

Detener, regenerar y limpiar

Para detener RustFS conservando sus objetos:

docker compose -f entorno/compose-s3.yml down

Para arrancarlo otra vez:

make -C entorno s3-up

Para eliminar el laboratorio S3, incluidos sus objetos locales:

docker compose -f entorno/compose-s3.yml down -v --remove-orphans

La opción -v no elimina los bloques HDFS, pero sí borra el volumen RustFS. Después será necesario ejecutar make -C entorno s3-up y volver a ejecutar el notebook.
