Sesión 6 — Hive Metastore, tablas Hive y Trino

Punto de la asignatura

Esta sesión viene después de S5. El alumnado ya ha visto que una colección de Parquet puede organizarse en directorios particionados y que Spark puede leerlos directamente. Ahora se introduce la capa que proporciona nombres y metadatos compartidos a los motores.

La pregunta central es:

¿Cómo pasamos de conocer una ruta física a disponer de una tabla lógica que puedan consultar Spark y Trino?

El Hive Metastore no es un motor de procesamiento y Trino no es el catálogo. El metastore conserva metadatos; Trino consulta y procesa; Spark puede utilizar la misma definición si se configura como cliente del catálogo.

Recorrido del curso

S2: Parquet sin tabla permanente
  → S3: Parquet en HDFS y S3-compatible
  → S4: Spark como motor
  → S5: organización refinada y particionada
  → S6: Hive Metastore y Trino comparten la tabla
  → S7: Iceberg añade gestión de tablas y snapshots

La infraestructura definida en entorno/compose-warehouse-hdfs.yml separa PostgreSQL, Hive Metastore, Trino y el clúster Hadoop. PostgreSQL almacena el repositorio del metastore; Hive Metastore expone la información por Thrift; Trino utiliza esa información para planificar consultas. Ninguno de esos servicios se convierte por ello en DataNode o NodeManager.

Capas que se deben distinguir

Capa Responsabilidad Ejemplo del laboratorio
Almacenamiento Conserva bytes y rutas HDFS bajo /datalake o /warehouse
Formato Describe cómo leer cada fichero Parquet
Metastore Guarda nombres, esquemas, ubicaciones y particiones Hive Metastore + PostgreSQL
Motor SQL Planifica y ejecuta consultas Trino
Motor de transformación Produce o consume DataFrames Spark
Formato de tabla Gestiona metadatos de tabla y cambios Iceberg en S7

Una ruta Parquet puede existir sin metastore. Una entrada del metastore no contiene todos los bytes de la tabla. Una tabla Hive externa puede apuntar a datos existentes y no debe borrar esos datos automáticamente al eliminar sólo su definición.

Objetivos docentes

Al terminar el bloque, el alumnado debería poder:

  • explicar qué problema resuelve un catálogo frente a una ruta física;
  • distinguir Hive Metastore, Trino, Spark y PostgreSQL;
  • registrar Parquet existente como tabla externa;
  • distinguir una tabla externa de una tabla administrada;
  • consultar ubicación, esquema y propiedades de una tabla;
  • inspeccionar las particiones conocidas por el metastore;
  • ejecutar consultas equivalentes desde Trino y Spark;
  • entender que una partición Hive combina una organización física con metadatos de catálogo;
  • observar selección de columnas, predicate pushdown y eliminación de particiones cuando el motor lo permite;
  • calcular estadísticas y explicar para qué sirven;
  • documentar el ciclo de vida y el riesgo de borrar datos gestionados;
  • identificar las limitaciones que justifican introducir Iceberg.

Tabla externa frente a tabla administrada

Se explicarán dos modelos distintos:

Tabla externa sobre el data lake

Una tabla externa registra la ubicación de Parquet que ya existe en /datalake. El catálogo añade nombre, esquema, formato y particiones, pero la fuente de datos continúa siendo externa al ciclo de vida de la tabla.

Este modelo es adecuado para los datos fuente y refinados de S2 y S5:

/datalake/raw/tpcds/date_dim
    → tabla Hive externa

/datalake/silver/tpcds/web_sales
    → tabla Hive externa particionada

/datalake/gold/tpcds/web_sales_by_year
    → tabla Hive externa orientada al consumo

Eliminar la definición de la tabla no debe interpretarse como permiso para borrar el data lake. Las operaciones destructivas sobre HDFS deben ser explícitas y documentarse.

Tabla administrada en el warehouse

Una tabla administrada deja que el catálogo y el motor elijan o gestionen una ubicación bajo /warehouse. En el laboratorio se utilizará esta zona para tablas de trabajo del catálogo y para las tablas Iceberg de S7.

El alumnado debe comprobar siempre la ubicación efectiva. El nombre lógico de una tabla y el directorio físico no tienen por qué coincidir exactamente.

Secuencia de la sesión

Registrar los Parquet originales

Primero se registrará una tabla Hive externa sobre una tabla pequeña, como date_dim, y después sobre una tabla de hechos. Se comprobará:

  • SHOW CREATE TABLE;
  • DESCRIBE;
  • la ubicación externa;
  • el esquema expuesto;
  • el número de filas;
  • la correspondencia entre los datos consultados y los Parquet de S2.

La primera consulta debe dejar claro que registrar una tabla no transforma automáticamente los datos ni los copia al warehouse.

Registrar la versión particionada

Después se registrará la salida de S5 con sold_year y sold_month. Se comparará una consulta sin filtro con otra que restrinja esas columnas. El alumnado debe observar qué directorios representan las particiones y qué información adicional conserva ahora el metastore.

El filtro debe utilizar las columnas de partición. Una consulta que transforma la columna de una manera que el planificador no pueda reconocer puede impedir la eliminación de particiones. La mejora no se debe deducir sólo del tiempo de pared: también se observarán el plan, el número de ficheros y las métricas disponibles.

Consultar con Trino

Trino se introducirá como motor SQL distribuido que utiliza el catálogo Hive. Se ejecutarán desde Trino:

  • SHOW SCHEMAS y SHOW TABLES;
  • SHOW CREATE TABLE;
  • DESCRIBE;
  • consultas sobre Parquet externos;
  • consultas sobre la versión particionada;
  • inspección de las particiones;
  • ANALYZE y consulta de estadísticas;
  • EXPLAIN o EXPLAIN ANALYZE cuando proceda.

Trino ofrece una tabla de metadatos $partitions para examinar las particiones de una tabla Hive y permite declarar tablas externas y propiedades de particionado. Conector Hive de Trino

Consultar la misma tabla con Spark

Una vez que Trino haya demostrado que la tabla está registrada, Spark se configurará como otro cliente del mismo metastore. Se leerá la misma tabla desde PySpark y se compararán:

  • nombre y esquema;
  • ubicación;
  • resultado de negocio;
  • columnas de partición;
  • plan de lectura;
  • comportamiento después de actualizar o añadir datos, considerando las cachés de metadatos.

No se debe presentar Spark y Trino como dos catálogos diferentes. Son dos clientes o motores que leen una definición compartida.

Buenas prácticas de catálogo y data lake

El metastore permite formalizar las decisiones de S5:

  • cada tabla tiene un propietario y una descripción;
  • la ubicación física está documentada;
  • el esquema y las claves tienen un contrato;
  • las columnas de partición se justifican por las consultas;
  • los ficheros auxiliares no se confunden con datos;
  • las estadísticas se generan y se revisan cuando son necesarias;
  • las tablas fuente y las tablas derivadas tienen ciclos de vida distintos;
  • una regeneración no borra datos ajenos;
  • las operaciones de limpieza están separadas de las consultas normales.

El metastore mejora la localización y reutilización, pero no proporciona por sí solo transacciones completas, historial de versiones ni una política de calidad de datos. Esas limitaciones preparan la comparación con Iceberg.

Evidencias de la sesión

La sesión debe demostrar comportamiento observable:

  • la tabla externa apunta a la ubicación esperada;
  • la tabla administrada utiliza /warehouse;
  • Trino devuelve el esquema y las filas esperadas;
  • las particiones se pueden enumerar;
  • una consulta filtrada reduce el trabajo cuando la organización y el predicado lo permiten;
  • las estadísticas cambian después de ANALYZE;
  • Spark y Trino consultan la misma definición;
  • eliminar metadatos externos no borra accidentalmente el data lake;
  • los permisos de luser son suficientes para los ejercicios.
